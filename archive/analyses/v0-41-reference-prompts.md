## CO-STAR-A Prompt for IDRM API Resource Mapping

### Context (C)
I am creating a comprehensive API Resource Mapping document for the Integrated Disaster Response Management (IDRM) MVP platform. The system has been fully designed across 12 categories with complete Low-Level Design documentation. The platform uses Python (FastAPI) for backend services and Node.js (Express) for the API Gateway/Edge layer. The API mapping needs to document every endpoint across all modules/components to serve as a reference for developers, testers, and stakeholders.

### Objective (O)
Create a complete, detailed API Resource Mapping in both Markdown and Excel (XLSX) formats that:
1. Lists ALL API endpoints across all IDRM modules/components
2. Documents request/response formats, authentication requirements, and access control
3. Provides clear purpose descriptions that even novices can understand
4. Follows the example format provided (Overview, Summary Mapping, Error Mapping sheets)
5. Organizes endpoints by module and component for easy navigation
6. Includes rate limiting, validation rules, and important notes
7. Serves as the definitive API reference for the development team

### Style (S)
- **Professional and precise**: Use standard REST API documentation conventions
- **Novice-friendly**: Write descriptions in plain English, explaining technical terms
- **Consistent formatting**: Follow the example structure exactly
- **Comprehensive coverage**: Include every endpoint from all 12 IDRM LLD categories
- **Actionable details**: Provide specific request/response examples
- **Clear organization**: Group by module → component → resource hierarchy

### Tone (T)
- **Instructive**: Explain what each endpoint does and why it exists
- **Clear and direct**: No ambiguity in endpoint purposes or requirements
- **Helpful**: Include notes on common use cases and edge cases
- **Respectful of novices**: Don't assume technical knowledge, explain concepts
- **Professional**: Maintain technical accuracy while being accessible

### Audience (A)
**Primary Audiences:**
1. **Backend Developers**: Need exact endpoint specs for implementation
2. **Frontend Developers**: Need to know how to call APIs, what data to send/receive
3. **QA/Testers**: Need to understand endpoints for test case creation
4. **API Gateway Developers**: Need to configure routing and rate limiting
5. **Project Managers**: Need overview of API landscape
6. **Novice Developers**: Need explanations of what each endpoint accomplishes
7. **Integration Partners**: May consume IDRM APIs in future

### Action (A)
**Step-by-step approach:**

1. **Create Overview Sheet** with IDRM project metadata
2. **Process each module iteratively** in this order:
   - Module 1: Authentication & Authorization
   - Module 2: Service Request Management
   - Module 3: Disaster Event Management
   - Module 4: Organization/Provider Management
   - Module 5: Geospatial Operations
   - Module 6: Real-time Communication (WebSocket)
   - Module 7: Notification Management
   - Module 8: Financial Operations
   - Module 9: Analytics & Reporting
   - Module 10: File Management
   - Module 11: User Management
   - Module 12: System/Admin Operations

3. **For each module**, document:
   - All CRUD endpoints (Create, Read, Update, Delete)
   - Search/filter endpoints
   - Special operation endpoints (approve, assign, match, etc.)
   - Include complete details: Method, Path, Request, Response, Auth, Roles, Rate Limits

4. **Create Error Mapping Sheet** with common HTTP status codes

5. **Export as:**
   - Markdown file (formatted tables, easy to read)
   - Excel XLSX file (matching example format exactly)

6. **Validate completeness** by cross-referencing with all 12 LLD category documents

**Deliverables:**
- `idrm-api-resource-mapping.md` (Markdown format)
- `idrm-api-resource-mapping.xlsx` (Excel format)
- Both files contain identical information in appropriate formats
- Complete coverage of all API endpoints from LLD documentation

**Quality Criteria:**
- ✅ Every endpoint from LLD is included
- ✅ Consistent naming conventions (REST best practices)
- ✅ Clear request/response data specifications
- ✅ Appropriate auth requirements per endpoint
- ✅ RBAC roles correctly assigned
- ✅ Rate limits defined based on endpoint sensitivity
- ✅ Novice-friendly descriptions
- ✅ No missing or ambiguous information

## CO-STAR-A Prompt for IDRM Data Modeling

### Context (C)
I am creating a comprehensive Data Model for the Integrated Disaster Response Management (IDRM) MVP platform. The system has complete Low-Level Design documentation across 12 categories and 105 API endpoints. The platform uses PostgreSQL 16 with PostGIS 3.4 for spatial data, managed through SQLAlchemy 2.0 ORM in Python. The data model needs to support all functionality described in the LLD including service requests, disaster events, provider management, geospatial operations, financial transactions, real-time updates, and analytics. The model must be normalized (3NF), optimized for performance with proper indexing, and include complete relationships, constraints, and data types.

### Objective (O)
Create a complete, production-ready Data Model documentation in both Markdown and Excel (XLSX) formats that:
1. Defines ALL database tables/entities with complete field specifications
2. Documents all relationships (one-to-many, many-to-many, etc.) with foreign keys
3. Specifies data types, constraints, defaults, and validation rules
4. Includes indexes (B-tree, GiST spatial, GIN text search) for performance
5. Provides ER diagrams using Mermaid for visualization
6. Includes both logical (entity-relationship) and physical (table) models
7. Documents enums, custom types, and domain-specific constraints
8. Shows database functions, triggers, and views where applicable
9. Provides sample data and usage examples for novice understanding
10. Serves as the definitive database schema reference for development

### Style (S)
- **Systematic and structured**: Organize by module/domain (Users, Services, Disasters, etc.)
- **Detailed specifications**: Every field with type, size, nullable, default, description
- **Visual diagrams**: ER diagrams in Mermaid showing relationships clearly
- **Normalized design**: Follow 3NF principles, eliminate redundancy
- **PostgreSQL-specific**: Use PostgreSQL data types (UUID, JSONB, GEOMETRY, etc.)
- **Performance-focused**: Document all indexes with rationale
- **Comprehensive**: Cover all 12 LLD categories and 105 API endpoints

### Tone (T)
- **Educational**: Explain database concepts for novices (primary key, foreign key, index, etc.)
- **Precise**: Use exact PostgreSQL terminology and syntax
- **Practical**: Show real-world examples and use cases for each table
- **Thoughtful**: Explain WHY design decisions were made
- **Professional**: Maintain technical accuracy while being accessible

7. **DBAs**: Need indexing strategy, performance considerations, maintenance plans
8. **Architects**: Need to validate design decisions and normalization

#### Phase 1: Core Entities (Foundation)

5. **Geospatial**

#### Phase 3: Support Entities (Infrastructure)
6. **Notifications**

  - Problem Statement (2 pages)

  - Recommendations (1-2 pages)

- Want to know impact on workflows

   - 3-bullet key findings

   - Scale: 1,000 documents, 20-min read each
   - Current pain points: Manual validation, drift detection, resource waste

   ```
   [Include detailed architecture diagrams for both deployment options]
   - Self-hosted: GitLab + Docker Compose + on-demand GPU
   - Cloud: GitHub Actions + AWS ECS/Lambda + spot instances
   ```

4. **Technology Stack Evaluation**
   | Component | Options Evaluated | Winner | Rationale |
   |-----------|------------------|--------|-----------|
   | Documentation Platform | Wiki.js, Docusaurus, GitBook | Wiki.js | Git-backed, AAA, WCAG |
   | Embeddings | multilingual-e5, LaBSE | multilingual-e5 | 100+ langs, 384-dim |

   ```
   Self-Hosted (GitLab):
   - Setup: 4 hours

   - Break-even for A100 ownership: 2,612 years (not viable)

   Cloud (GitHub + AWS):
   - Setup: 2 hours
   - Monthly: $74 (ECS $15 + RDS $17 + ALB $16 + ElastiCache $13 + misc $12 + GPU $1)
   - 5-Year TCO: $4,440
   - Auto-scaling: Yes
   - Managed services: 90%

   Savings with Cloud: $1,020 over 5 years (18.7%)
   ```

     - Utilization: 0.18% (16 hours/year out of 8,760)
     - Waste: $32,581

     - Cost: $18.72 over 5 years
     - Utilization: 100% (pay only when running)
     - Providers: Vast.ai ($0.78/hr), RunPod ($0.99/hr)

7. **Implementation Roadmap**
   - Week 1: Infrastructure setup (Terraform/Docker Compose)
   - Week 2: Wiki.js configuration, Git sync
   - Week 3: CI/CD pipeline, GPU orchestration
   - Week 4: Validation testing (100 doc subset)
   - Week 5: Production rollout

8. **Risk Matrix**
   | Risk | Probability | Impact | Mitigation |
   |------|------------|--------|------------|

   | LLM hallucination | 1-2% | Medium | Ensemble validation, human review |
   | Over-reliance on automation | Medium | Medium | Sample 10% for human QA |
   | Cost overruns (AWS) | Low | High | Budget alerts, reserved instances |

   ```
   Choose Self-Hosted (GitLab) if:
   ✓ Government/compliance requires on-premise
   ✓ Strong DevOps team available
   ✓ Full data control is non-negotiable
   ✓ Existing on-premise infrastructure
   ✓ Open-source preference

   Choose Cloud (GitHub + AWS) if:
   ✓ Want minimal maintenance
   ✓ Need auto-scaling
   ✓ Team uses GitHub already

   ✓ Value reliability (99.99% SLA)
   ```

10. **Recommendations**
    - **For 80% of organizations:** GitHub + AWS
      - Lower TCO, less maintenance, better reliability
      - Optimizations: Reserved instances, Savings Plans → $45/month achievable

      - Full control, air-gapped option, audit-friendly

    - B: Docker Compose file

## 🚀 Complete Tutorial: Building an AI-Powered Multilingual Documentation Validator

### Part 1: Understanding the System (Beginner-Friendly)

#### What Are We Building?

Imagine you have documentation in English, and translators have created versions in Hindi, Telugu, Tamil, and 7 other languages. How do you ensure the Hindi version says the same thing as English? That the Telugu version didn't miss an important safety warning?

**This system automates that check using AI.**

##### The Magic Ingredients

1. **Embeddings** (Think: Document Fingerprints)
   ```
   "Installation requires admin rights" (English)
   → [0.23, -0.41, 0.19, ...] (384 numbers)
   
   "स्थापना के लिए व्यवस्थापक अधिकार आवश्यक हैं" (Hindi)
   → [0.24, -0.39, 0.18, ...] (384 numbers)
   
   These numbers are VERY similar → Good translation! ✅
   ```

2. **Cosine Similarity** (Think: Measuring Fingerprint Closeness)
   ```python
   similarity = 0.92  # 92% similar
   threshold = 0.85   # Our acceptable minimum
   
   if similarity >= threshold:
       print("✅ Translation is semantically equivalent!")
   else:
       print("⚠️ Translation may have drifted, needs review")
   ```

3. **LLM Deep Check** (Think: Expert Second Opinion)
   - For borderline cases (similarity 0.75-0.85)
   - AI reads both versions deeply
   - Reports specific issues: "Technical term 'API' translated as 'interface' - may confuse developers"

##### How Often Does This Run?

**Only when documents change!** That's the key cost-saver.

- You edit `getting-started.md` in English
- Push to Git
- System automatically:
  1. Provisions GPU ($0.78/hr spot instance)
  2. Validates English vs all 10 translations (20 min)
  3. Reports issues
  4. Terminates GPU
- **Cost per run:** $0.26

**For your use case:** 100 docs change per run, 4 runs/month = $1.04/month GPU cost

💡 **Pro Tip:** This is why we DON'T self-host an A100. It would sit idle 99.8% of the time costing $550/month!

#### Option A: Self-Hosted GitLab (If You Want Full Control)

##### Step 1: Prepare Your Server

```bash
## SSH into your server
ssh root@your-server-ip

## Update system
apt update && apt upgrade -y

## Install Docker (the easy way)
curl -fsSL https://get.docker.com | sh

## Verify Docker works
docker run hello-world
## ✅ You should see: "Hello from Docker!"

## Install Docker Compose
curl -L "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose
chmod +x /usr/local/bin/docker-compose

## Verify
docker-compose --version
## ✅ Should show: docker-compose version 1.x.x
```

##### Step 2: Clone and Configure

```bash
## Clone the repository
cd /opt
git clone https://github.com/yourorg/docs-validation.git
cd docs-validation/gitlab-selfhosted/

## Create your config from template
cp .env.example .env

## Edit configuration (use nano or vim)
nano .env
```

**What to put in .env:**
```bash
## Your domain or IP
DOMAIN=docs.yourdomain.com  # or use: DOMAIN=123.45.67.89

## Your email (for SSL certificates)
EMAIL=admin@yourdomain.com

## Create a strong password (command to generate one):
## openssl rand -base64 32
GITLAB_ROOT_PASSWORD=YourSuperSecurePassword123!

## Database passwords (generate unique ones)
POSTGRES_PASSWORD=$(openssl rand -base64 32)
WIKIJS_DB_PASSWORD=$(openssl rand -base64 32)

## Get from Vast.ai → Account → API Key
VASTAI_API_KEY=paste_your_key_here
```

💡 **Pro Tip:** Keep your .env file secret! Add it to .gitignore.

## Watch the magic happen (takes 5-10 minutes)

## ✅ Databases initializing
## ✅ GitLab booting up (this is slowest, ~5 min)
## ✅ Wiki.js ready

#### Troubleshooting Common Issues

##### Issue: "GPU provisioning failed"

```bash
## Check API key is correct
## Self-hosted:
docker exec gitlab-runner printenv | grep VASTAI

## AWS:
aws lambda invoke \
  --function-name gpu-orchestrator \
  --payload '{"action": "test"}' \
  response.json
cat response.json
```

**Fix:**
- Verify API key in .env
- Check Vast.ai account has credit
- Try alternative provider (RunPod)

##### Issue: "Validation takes too long"

Expected: ~20 minutes for 100 documents

If longer:
- Check GPU instance specs (should be A100)
- Look for network issues in logs
- Consider batch optimization

##### Issue: "High costs"

```bash
## Identify cost culprit
## AWS:
aws ce get-cost-and-usage \
  --time-period Start=2025-01-01,End=2025-01-31 \
  --group-by Type=SERVICE
```

**Common causes:**
- GPU not terminating (check Lambda logs)
- Too many validations (review trigger logic)
- Data transfer costs (enable CloudFront)
