① The plan & outline

What this is

A complete set of sample page templates for the IDRM MVP web surface, built in the attached Slate + Emerald design language. Use them as a visual spec and a starting point for the real HTML/Tailwind (citizen) and React (admin) builds.

Every template is a visual mockup with realistic data. The exact backend calls each page makes are written in a dashed “API ·” note on the page and in code comments — nothing here needs a running server.

Authoring happens on Windows; building/running happens on the Ubuntu target. These files open in any browser, offline.

② Design system at a glance

🎨 Color

Slate neutrals + Emerald primary. Page #f8fafc, surfaces white, headings #0f172a, body #334155, primary #059669 (use #047857 for small text/buttons to clear AA).

🔤 Type & rhythm

Inter. Scale 12→36px. Body line-height 1.75× (per spec); headings tighter for hierarchy. Spacing on a 4px grid.

📱 Responsive

Mobile-first; verified at 360 / 768 / 1280. Nav collapses to a burger; citizen pages get a bottom tab-bar; tables scroll; tap targets ≥ 44px.

♿ Accessible

Semantic HTML, one h1/page, visible focus rings, role="alert", labelled fields. Status & priority never rely on color alone — always text + icon.

🧩 Components

Buttons, cards, forms, badges, alerts, tables, timelines, stat cards, map canvas, drawers, toasts — all from shared tokens (no new hex).

🔌 Data

UPPERCASE enums; GET/POST only with action endpoints (/approve, /accept…). Canonical roles per FS §3.3.

④ Request lifecycle

Every service request moves through these states. Emergency/urgent requests are auto-approved by the system.

SUBMITTED→ APPROVED→ ACCEPTED→ IN_PROGRESS→ COMPLETED→ VERIFIED

Branches: REJECTED CANCELLED EXPIRED (terminal) · DISPUTED (from IN_PROGRESS/COMPLETED → back to IN_PROGRESS or REJECTED).

⑤ User workflows — use-case scenarios

Step-by-step journeys per role. Each step names the page it happens on and the resulting status.

🆘 Scenario A — A citizen requests help (the core loop)

Actor: Citizen · Goal: get an ambulance during a flood.

  1. Lands on Home → taps Request help.
  2. Creates an account on Register (or Login).
  3. Arrives at the Dashboard → + New request.
  4. On Create request: picks MEDICAL + CRITICAL, drops a map pin, sets privacy → submits. SUBMITTED → auto APPROVED.
  5. Watches Service detail as a provider accepts and arrives. ACCEPTED → IN_PROGRESS → COMPLETED.
  6. Confirms completion and rates ★. VERIFIED.

📋 Scenario B — A citizen tracks & manages requests

Actor: Citizen · Goal: review and cancel a no-longer-needed request.

  1. Opens My requests → filters by status/type.
  2. Opens a Service detail still SUBMITTED.
  3. Taps Cancel request with a reason → CANCELLED (allowed only while SUBMITTED/APPROVED).
  4. Reads updates anytime on Notifications.

🏥 Scenario C — A provider delivers relief

Actor: Provider (NGO/hospital) · Goal: accept and complete nearby work.

  1. Signs in to the Provider dashboard (capacity, counts).
  2. Browses Available services matching their service types within radius → Accept (sets ETA). APPROVED → ACCEPTED.
  3. On Active services: Start work → IN_PROGRESS, then Mark complete → COMPLETED.
  4. Requestor verifies; the assignment closes. (A problem can be flagged → DISPUTED.)

🏛️ Scenario D — An authority approves & coordinates

Actor: DM_AUTHORITY (Event Admin — GO or vetted NGO) · Goal: clear the queue and resolve a dispute.

  1. Opens the Admin dashboard → Approval queue.
  2. Approve valid non-urgent requests (urgent ones were auto-approved) or Reject with a reason. APPROVED / REJECTED.
  3. For a DISPUTED item: Reassign → IN_PROGRESS, or mark Invalid → REJECTED.
  4. Monitors KPIs, breakdowns and the audit log.

🛡️ Scenario E — An admin oversees the platform

Actor: ADMIN · Goal: manage users and watch system health.

  1. On the Admin dashboard: reviews KPIs and the audit trail.
  2. Searches Users, verifies providers, grants elevated roles (POST /users/{id}/role).
  3. Uses the full React admin suite (port 5174) for exports, heatmaps and deep management.

👁️ Scenario F — The public (not logged in)

Actor: Public visitor · Goal: understand the situation; decide to act.

  1. Reads Home and views the Live map read-only.
  2. To request help or volunteer, is prompted to Register (enters Scenario A / C).

How IDRM works

📝

1 · Request

Pin your location on the map, pick a service type (medical, food, water, shelter…) and describe what you need. Three taps or fewer.

✅

2 · Match

Authorities approve the request (instantly for emergencies) and the nearest available provider accepts and heads your way.

📍

3 · Track

Watch status update live — accepted, in progress, completed — then confirm and rate the help you received.

Built for everyone in the response

👥 Citizens & volunteers

Request help for yourself or report needs in your area. Works on cheap phones and slow networks.

🏥 Providers (NGOs / hospitals)

See nearby approved requests that match your services and capacity, accept, and deliver.

🏛️ Authorities & admins

Declare disaster events, approve requests, coordinate providers, and monitor the whole picture.
