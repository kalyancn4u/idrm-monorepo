(cross-cutting standards — apply to ALL work; read before writing guides)
------------------------------------------------------------------------
A) GUIDES QUALITY BAR (every guide, MVP and FFP):
   Clear and precise, YET elucidated in lucid detail — written so a
   COMPLETE NOVICE can follow it and reach MASTERY. Concretely:
     - Define every term on first use; expand every acronym once.
     - Assume no prior context; build from first principles, then deepen
       progressively (basics -> intermediate -> advanced) without gaps.
     - Show worked, copy-pasteable examples and expected output.
     - Explain the WHY, not just the HOW; call out common pitfalls.
     - Plain language over jargon; when jargon is unavoidable, teach it.

B) UNIVERSAL ENGINEERING PRINCIPLES (project-wide, tech-neutral):
   All code — MVP and FFP, AI-generated or human-written — MUST honor:
     - SOLID, DRY, KISS, Separation of Concerns
     - High Cohesion / Low Coupling, Composition over Inheritance
     - Reusable component architecture, Type Safety, Accessibility-First
   These are PHASE-NEUTRAL; they manifest differently per stack:
     - MVP: Python type hints + Pydantic + mypy (type safety);
       Jinja partials / small JS modules (reusable components);
       semantic HTML + ARIA + WCAG (accessibility-first).

1. WHAT IDRM IS
------------------------------------------------------------------------
IDRM = Integrated Disaster Response Management. An India-focused, web-based,
map-driven platform connecting disaster-affected people with the
organizations/responders that can help them (incidents, resources, volunteers,
alerts, coordination, reporting). "Uber for disaster relief."
Authoritative product vision = top-level ../posters/ + the finished ../docs/ set.
THIS archive is where the clean MVP + FFP documentation was built.

------------------------------------------------------------------------
2. THE CENTRAL MENTAL MODEL — TWO PHASES: MVP and FFP
------------------------------------------------------------------------
MVP = Minimum Viable Product (BUILD FIRST). Deliberately simple:
  - Pure-Python FastAPI MODULAR MONOLITH (one deployable app, clean modules)
  - Web UI = HTML + Tailwind CSS v4 + JavaScript + Leaflet (NO React, NO Bun)
  - PostgreSQL 16 + PostGIS 3.4 = single source of truth
  - MinIO (S3-compatible) = object storage for uploads (IN MVP)
  - Pydantic, SQLAlchemy, GeoAlchemy2, Alembic, pytest, Git
  - NO Redis, NO microservices, NO React/Expo, NO brokers, NO Docker/K8s,
    NO GeoServer. All deferred to FFP.

FFP = Full-Fledged Product (NEXT PHASE, "if/when a trigger justifies it").
The enterprise evolution the MVP grows into WITHOUT a rewrite (same API
contract, same module boundaries):
  - Selective MICROSERVICES (extract one module at a time, least-coupled first,
    Strangler Fig pattern, on a concrete trigger)
  - API GATEWAY = APISIX (plugins for reverse proxy, caching, auth, rate-limit,
    TLS, routing, LB, observability). NOT NGINX.
  - Bun/Node/Deno = edge/BFF/websocket/SSR services BEHIND APISIX (not the gateway)
  - POLYGLOT runtimes: Java/Go/JS for scale/security/resilience-critical services;
    PYTHON kept for rapid prototyping + DS/ML. Per-service, as time permits.
  - React (web SPA) + React Native/Expo (mobile), same APIs
  - Redis/Redis Streams -> RabbitMQ/Kafka, workers/queues
  - Docker -> Swarm/Kubernetes, CI/CD, distributed observability, HA/scale
  - Per-service data ownership; PostGIS stays the system of record
  - Python geospatial service (GeoPandas/Shapely), NOT Java GeoServer

RULE: when MVP work meets Redis/microservices/React/Bun/Docker/etc., it is NOT
dropped — it is routed to the FFP charter/docs and recorded as a deferral.

4. LOCKED DECISIONS (confirmed by the user — do NOT re-litigate)
------------------------------------------------------------------------
MVP:
  - Modular monolith (FastAPI/Python); advanced tech = FFP.
  - Web UI = HTML + Tailwind CSS v4 + JS (+ Leaflet). No React, no Bun/Node.
  - PostgreSQL 16 + PostGIS 3.4 = sole source of truth.
  - MinIO (S3-compatible) for file/object storage — IN the MVP (uploads:
    incident photos, completion proof). DB stores only keys/URLs, not blobs.
  - NO Redis (sessions in Postgres), NO Docker/K8s (native systemd on Ubuntu),
    NO brokers, NO GeoServer.
  - CANONICAL API (frozen): incident-centric, version-in-path "/api/v1/...",
    snake_case, UUID ids, ISO-8601 UTC "*_at", lowercase snake_case enum values,
    lists wrapped "{data,pagination}" / singles = bare object, error envelope with
    machine "code". URIs are a STABLE CONTRACT across the whole SDLC (FFP only
    ADDS endpoints at the same paths; never renames). OpenAPI validated.
    UI term "help request" == API resource "incident".
  - Auth: RS256 JWT (access ~60min + rotating/revocable refresh ~7d), RBAC over
    4 roles (citizen, provider, coordinator, admin) + a narrow guest path.
    NIST-aligned password policy (length>composition, bcrypt cost 12), 5-attempt
    /15-min lockout. OIDC/SSO, MFA, ABAC, full role hierarchy + Auditor = FFP.
  - Lean incident lifecycle (8 states): created -> (approved, if critical) ->
    accepted -> in_progress -> completed -> verified, plus cancelled/rejected.
    (Disputed + auto-close = FFP.)
  - File upload = IN MVP. Media rules: compress-on-device, files <=10MB (PDFs
    <=~1.5MB/page), photos resized <=1920px, >=640x480, blur-checked, EXIF/GPS
    stripped; emergency "lite" = one <=~500KB photo. Face DETECTION-only quality
    gate (nothing biometric stored). FaceNet RECOGNITION/matching = FFP (DPDP Act
    2023 consent).
  - Out of MVP -> FFP: money/donations, disaster-event entity + COP, per-request
    privacy levels (Public/Protected/Private), AI matching, national rollout,
    advanced analytics, full localization, multi-channel intake, deep real-time push.
  - PRD is TECH-FREE (needs only; tech lives in the architecture doc).
  - Native geospatial via PostGIS + Python (dedicated GIS server only if FFP needs).

FFP:
  - Selective microservices on a trigger (scale/ownership/deploy/perf/reliability),
    least-coupled first (auth), Strangler Fig, public API contract preserved.
  - APISIX gateway (NOT NGINX); Kong evaluated as the alternative and NOT chosen
    for the free/open build — rationale in Section 4A. Bun/Node/Deno = edge behind it.
  - Polyglot (Java/Go/JS + Python-for-DS/ML). Per-service data ownership.
  - React web + React Native/Expo; Redis->brokers+workers; Docker->K8s.
  - Python geospatial service (GeoPandas/Shapely), not Java GeoServer.
  - FFP set MIRRORS the MVP set 1:1 + one Messaging&Async doc = 12 docs (FROZEN)
    + 1 companion (61-frontend-engineering-standards). See Section 6.

13. MARKDOWN LINKS — HOW TO OPEN THEM (VS Code & other renderers)
------------------------------------------------------------------------
SYMPTOM (reported 2026-08-16): a link in a README/doc underlines on hover ("looks clickable") but a normal
click does NOT open the target .md in VS Code. ROOT CAUSE: this is NOT a broken link — every cross-link in the
doc set is a verified relative path. It is how each Markdown tool treats a click. Use the right gesture per
context; NO file edits are ever needed for links to work.

WHY IT HAPPENS + WHAT TO DO (per use-case):
  * VS Code — SOURCE EDITOR (the raw .md you are typing in): a plain left-click only moves the text cursor.
    You must FOLLOW the link with **Ctrl+Click (Windows/Linux)** or **Cmd+Click (macOS)**. The hover tooltip
    literally says "Follow link (ctrl/cmd + click)". This is VS Code's designed behaviour — nothing to fix.
  * VS Code — MARKDOWN PREVIEW (open it with **Ctrl+Shift+V**, or Cmd+K then V): links follow on a **single
    plain click**. By default, clicking a link to another .md opens THAT file's *preview*. To make it open the
    real file in the editor instead, this repo already ships **`.vscode/settings.json`** with:
        "markdown.preview.openMarkdownLinks": "inEditor"   (+ markdown.validate.enabled to flag broken links)
    So on opening the repo folder, Preview single-clicks open the actual file with no reader setup. (The raw
    EDITOR still needs Ctrl/Cmd+Click — that is built-in and no setting can change it.)
  * GitHub / GitLab / most web renderers: links follow on a single click automatically.
  * Obsidian / other editors: usually single-click; a few dislike %20-encoded spaces — see below.

PREREQUISITES for relative links to resolve (all already satisfied by this repo):
  - **Open the FOLDER/repo as a workspace** (File -> Open Folder), not a single loose .md. Relative links
    (e.g. ../ffp/... or ../../guides/...) resolve against the file's own location; a lone file has no folder
    context, so links appear dead.
  - Keep the tree intact (docs/, archive/, guides/, posters/ as siblings under the repo root).

FILENAMES WITH SPACES (e.g. "IDRM MVP Architecture - CO-STAR Prompt.md"):
  - Linked with %20 for each space: (IDRM%20MVP%20Architecture%20-%20CO-STAR%20Prompt.md). VS Code and GitHub
    decode %20 and open these correctly. If a future tool does not, the seamless fix is to give NEW files
    kebab-case, space-free names — do NOT hand-edit existing links.

AUTHORING RULES (so links stay seamless with zero manual fixes later):
  1. Always write [label](relative/path.md); the path is relative to THE FILE being edited.
  2. Base docs (docs/mvp, docs/ffp) and archive docs (archive/idrm-*-docs) sit at DIFFERENT depths, so the
     same cross-link needs different ../ prefixes in each copy — edit prose identically but keep link prefixes
     per-layout, and keep both copies in sync (see §9-E sync rule; the relink pattern base<->archive:
     ../../guides/mvp/ <-> ../idrm-mvp-guides/ , ../../archive/instructions/ <-> ../instructions/ ,
     ../ffp/ <-> ../idrm-ffp-docs/ , ../mvp/ <-> ../idrm-mvp-docs/).
  3. Prefer kebab-case, space-free filenames for anything new (avoids %20 entirely).
  4. Verify after editing: a link is correct if the target file exists at the resolved relative path
     (the scratchpad checker greps ]\(path\) and tests each path exists).
