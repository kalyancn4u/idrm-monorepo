# Typed API Clients

## What this document is

Every React-based frontend in IDRM talks to the backend through one shared,
typed client. This document explains what that client is, why it exists, and
how it stays in sync with the backend.

## The problem it solves

Without a shared client, each frontend writes its own HTTP calls. One team
uses fetch, another uses axios. One attaches the auth token correctly,
another forgets. One parses errors one way, another parses them differently.
The system becomes three incompatible clients pretending to be one product.

Worse: when the backend renames a field or removes an endpoint, nothing
breaks at compile time. The break happens at runtime, in production, often
only for a specific user path. Silent failures are the most expensive kind.

## The solution: generate the client from the contract

The typed client is generated from the OpenAPI specification in
shared/contracts/v1/. The chain is:

    shared/contracts/v1/openapi.json  (the source of truth)
            |
            v
    packages/api-client/              (generated by Kubb)
            |
            +--> apps/web-react/      imports @idrm/api-client
            +--> apps/mobile/         imports @idrm/api-client
            +--> apps/web/            uses the spec directly

There is one contract, not three. When the backend changes, the contract is
regenerated, the client is regenerated, and every app that imported the
client either compiles or fails. Compile-time validation replaces runtime
guessing.

## What the client handles automatically

| Concern | Handled by the client |
|---|---|
| URL construction | Path parameters interpolated from typed inputs |
| Query serialisation | Arrays, booleans, dates encoded per OpenAPI style |
| Request body encoding | JSON, form-data, multipart, content-type inferred |
| Auth token injection | Resolved from OpenAPI security schemes |
| Error parsing | Status-keyed results or thrown typed errors |
| Response typing | Inferred from OpenAPI schema |
| Runtime validation | Optional, via Zod or TypeBox integration |

## What you write in a frontend

    import { listIncidents, createIncident } from '@idrm/api-client';

    const incidents = await listIncidents({ status: 'open' });
    // incidents is typed: Incident[]

    const created = await createIncident({ title: 'Flood', location: '...' });
    // created is typed: Incident

No manual fetch, no manual URL building, no guessing at shapes.

## How to regenerate

From the repository root:

    make contracts-export      refresh the OpenAPI spec from the backend
    make contracts-validate    lint the spec
    make contracts-generate    regenerate this package
    make contracts-sync        all three steps in order

## The build-time guarantee

When the contract changes:

1. The generation step re-runs.
2. packages/api-client/ is updated.
3. Every app that imports the client is rebuilt.
4. If an app used a field that no longer exists, the build fails.

This is not a runtime check. It is a build-time guarantee. The failure is
loud, immediate, and cheap to fix.

## Rules

1. Never hand-edit anything under packages/api-client/src/gen/.
2. Never commit a regenerated client without the contract change it reflects.
3. If a build fails after regeneration, fix the app. Do not weaken the types.

## Why this matters especially in a polyglot monorepo

The backend may be Python, Go, Java, and TypeScript in different services.
Each language has its own HTTP conventions. The typed client normalises all
of that. Regardless of which service implements an endpoint, the frontend
sees the same typed function.
