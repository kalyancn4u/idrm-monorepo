# IAM 101

> *Type: Guide (101 / foundational) · Audience: novices → developers · Status: MVP — current · Track: Security (#18)*
> *IAM decides **who you are** and **what you're allowed to do** — the front door to the whole system. This guide
> explains it from scratch, then walks IDRM's actual login and token design.*

---

## 1. What IAM is

**IAM = Identity and Access Management** — the discipline of proving who a user is and controlling what they can
reach. It rests on two words people constantly confuse:

- **Authentication (AuthN)** — *who are you?* (proving identity: username + password, etc.)
- **Authorization (AuthZ)** — *what may you do?* (permissions once your identity is known)

> A hospital badge is a good analogy: showing your photo ID is **authentication**; the doors your badge opens are
> **authorization**. IDRM needs both, because a citizen and a government coordinator must see very different things.

---

## 2. Credentials, sessions, and tokens

- **Credential** — the secret that proves identity (a password; later, a second factor).
- After you log in, the server needs to *remember* you across many requests. Two common ways:
  - **Session** — the server keeps a record and hands you an id (IDRM MVP keeps sessions in **PostgreSQL** — no
    Redis in the MVP).
  - **Token** — a signed digital "pass" you present on each request. IDRM uses tokens (JWT, below).

---

## 3. JWT — IDRM's access pass

**JWT = JSON Web Token** — a compact, signed token carrying claims like *who you are* and *your role*. Because it's
**cryptographically signed**, the server can trust it wasn't tampered with, without storing it.

IDRM's design (locked):

- **RS256 signing** — an asymmetric signature (a private key signs; a public key verifies). Safer for
  multi-service futures than a shared secret.
- **Two tokens:**
  - **Access token** — short-lived (~60 min), sent on every API call in the `Authorization: Bearer …` header.
  - **Refresh token** — longer-lived (~7 days), **rotating and revocable**, used only to get a fresh access
    token so you don't log in constantly.
- **Storage:** access token in memory; refresh in a secure httpOnly cookie / device store. **Never** in
  `localStorage` (a cross-site scripting attack could steal it).

---

## 4. Protecting passwords

Even the best token design fails if passwords are weak or stolen. IDRM follows NIST-aligned rules:

- **Length beats complexity** — long passphrases over forced symbol soup.
- Passwords are **hashed with bcrypt (cost 12)** — never stored in plain text; a hash can't be reversed.
- **Lockout:** 5 failed attempts within 15 minutes locks the account, blunting brute-force guessing.

---

## 5. IDRM's roles (the AuthZ side)

Once authenticated, **authorization** decides access by **role**: `citizen`, `provider`, `coordinator`,
`admin`, plus a narrow **guest** path. *How* roles grant permissions is the next guide,
[RBAC/ABAC 101](rbac-abac-101.md).

**Defense in depth:** the UI hides what you can't do, but the **server re-checks every request** — hiding a button
is convenience, never the security boundary.

---

## 6. What FFP adds (context)

The MVP keeps IAM lean. The enterprise phase adds **OIDC** (federated login), **OAuth 2.1 + PKCE** (secure
delegated access), **MFA** (a second factor), and **ABAC** (attribute-based rules) — see
[`../../instructions/security.md`](../../../archive/instructions/security.md). These have their own 101 guides in the
Security track.

## 7. Mastery check

1. Explain **authentication vs authorization** with an IDRM example of each.
2. Contrast a **session** and a **token**; say which IDRM MVP uses and where sessions live.
3. Explain **JWT**, why **RS256**, and the roles of the **access** vs **refresh** token.
4. Say why passwords are **bcrypt-hashed** and what the lockout rule is.
5. Explain "defense in depth" — why UI hiding isn't security.
